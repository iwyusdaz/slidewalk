# Agent review — slidewalk (2026-10-31)

**Disclosure and scope limitation:** this is an **Agent review**, performed by a reviewer agent working in a fresh context that did not build the repository. It may run on the same underlying model family as the agent that built the repository. It is therefore a usability/correctness review by a similar AI system — **not an independent evaluation and not a substitute for human review**. It is also not an accessibility audit: no screen reader, no disabled user, no educator was involved. All conclusions below are based only on the repository files, the README, and commands run from the repo root on 2026-10-31.

This review follows `evaluation/REVIEWER-BRIEF.md`. Section 1 is the honesty audit; sections 2–7 are the brief's checks; findings are summarized with severities in section 8.

Severity scale used: **High** (misleading claim, broken functionality), **Medium** (accuracy/robustness gap that should be addressed), **Low** (cosmetic, minor UX, or worth noting only).

## 1. Honesty audit

Searched the whole repo (excluding `node_modules/`, `.venv/`) for compliance/certification language (`certif`, `complian`, "WCAG compliant", "fully accessible").

- **No compliance or certification claims found anywhere.** The dominant phrasing is exactly the required one: "gated against WCAG 2.1 A/AA automated checks" appears in README ("Accessibility" section), `docs/accessibility-statement.html` ("nothing here claims WCAG conformance or certification"), and `evaluation/METHODS.md` ("Honesty rules applied here"). `docs/index.html` states "no compliance or certification is claimed".
- **Checkpoint slides are labeled as auto-generated** on the slides themselves (`<p class="checkpoint-label">Auto-generated retrieval prompt — review before teaching</p>` on slides 7 and 11 of `docs/deck.html`), in each slide's speaker notes, in the facilitator guide header, in `guide.mjs` output ("CHECKPOINT (auto-generated)"), and in the deck JSON (`autoGenerated: true`). Each cites its source slide (`checkpoint-source` / "Drawn from:").
- **AI assistance is disclosed in the README** ("Honest limitations" → "AI assistance: this toolchain and its reference content were built with AI assistance and reviewed by the repository owner…"), and again on `docs/index.html` and `docs/accessibility-statement.html` context.
- **Pending human review is not faked:** `evaluation/METHODS.md` keeps the educator-review table empty with an explicit PENDING row; `evaluation/human-protocol/educator-review-template.md` is an unfilled protocol.

**Findings:**

- **[Fixed, was Medium] README and `docs/index.html` claimed "the deck's own footer … says so" (that manual testing is recommended), but the deck footer contained only the keyboard hint and navigation controls.** The facilitator guide did say so; the gate output did not. Fixed by (a) adding the disclaimer line to the deck footer in `skill/scripts/build-html.mjs` and regenerating `docs/deck.html` and the three theme probes (regeneration from the committed `deck.json` produced a one-line diff, confirming the artifacts were otherwise reproducible), and (b) adding a reminder line to `tooling/run-gates.mjs` pass output. All gates re-run green after the change (section 2).
- **[Low, open] The gate runner's no-trap check is shallow:** it presses Tab 8 times and asserts focus is not on `<body>`. A real trap (e.g. focus forced back into one element by script) could still pass. Recorded as an open hardening idea, consistent with the README's next steps.

## 3. HTML deck quality (`docs/deck.html` source review)

- **lang attribute:** `<html lang="en">` present, sourced from outline front matter. PASS.
- **Heading structure:** exactly one `<h1>` (deck title, top bar); every slide title is an `<h2>`; speaker notes use `<h3>`. No skipped levels; the gate asserts this on every run.
- **Keyboard navigation:** arrow keys, Space, PageUp/PageDown, Home/End; `N` toggles speaker notes; buttons set `aria-expanded`/`aria-pressed`. After each navigation, focus moves to the visible slide's `<h2 tabindex="-1">` — correct focus management. Initial page load deliberately does not steal focus (reasonable).
- **No focus trap:** non-visible slides carry the `hidden` attribute (removed from tab order); the only tab stops are the skip link, heading, toolbar buttons, and the `tabindex="0"` pre block is on the site pages, not the deck. Verified by the gate traversal plus manual code reading.
- **Slide semantics:** each slide is `<section role="group" aria-roledescription="slide" aria-label="Slide N of 17: …">`; the slide counter is `aria-live="polite"`. Skip link to the first slide included.
- **Deep links:** `#s7`-style hashes are supported and updated via `history.replaceState` (no history spam).

**Findings:**

- **[Low, open] Space while a toolbar button is focused advances the deck instead of activating the button.** The global `keydown` handler calls `preventDefault()` on Space for any target that is not an input/textarea, which suppresses the button's own Space activation. Consequence: pressing Space with "Previous slide" focused moves forward rather than back, and the notes toggle does not respond to Space (only Enter or the click). This is arguably intentional deck-player behavior (Space always means "next"), and the gates test Space from an unfocused state, so nothing fails — but it is a small keyboard-behavior wart worth a deliberate decision. Left open (behavioral change, not an unambiguous typo-level fix).
- No other issues: title element, meta description, `prefers-reduced-motion`, print layout with notes, and 320px fluid type via `clamp()` are all present in the template.
